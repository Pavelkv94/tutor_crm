# Оплаты через Stripe — что нужно сделать на фронтенде

Бэкенд-фича «оплаты и баланс» реализована и покрыта тестами. Этот документ — исчерпывающее ТЗ для фронтенд-агента: что сломалось, что появилось, и по каким правилам это должно вести себя в интерфейсе.

Фронтенд: `frontend-vite/` (React 19 + Vite 7 + TailwindCSS 3 + shadcn/Radix, `@tanstack/react-query`, axios-клиент `src/lib/api-client.ts`, путь `@/` → `src/`).

Актуальная спецификация API — `backend/swagger.json` (регенерирована). Swagger UI в дев-режиме: `/api/swagger`.

---

## 0. TL;DR — минимум, без которого фронтенд сломается

1. **`Student.payment_currency` → `Student.balance_currency`**, тип стал **nullable**. Поле переименовано и в ответах, и в теле запросов create/update.
2. **`Student.balance`** переехал из `StudentExtended` в базовый `Student` — теперь приходит и в списках, а не только в карточке.
3. **`CreatePlanInput.plan_currency`**: значения `USD` и `RUB` удалены, остались `EUR | PLN | BYN`.
4. Всё остальное — новая функциональность, ничего не ломает.

## 1. Ломающие изменения в существующих контрактах

### 1.1 Валюта ученика: `payment_currency` → `balance_currency`

Раньше это было постоянное свойство ученика («в чём он платит»). Теперь это **валюта текущего остатка на балансе**, и она живёт по правилам:

- `balance = 0` ⇒ `balance_currency = null`. Валюта «отпущена», ученик может перейти на любую другую.
- `balance ≠ 0` ⇒ `balance_currency` заполнена и **менять её нельзя**, пока остаток не обнулится.
- Валюта расчётов выводится из планов назначенных занятий, а не задаётся вручную.

После миграции **у всех существующих учеников `balance_currency = null`** (прежнее значение `BYN` было артефактом дефолта и никакой информации не несло).

**Затронутые файлы фронтенда** (найдены по `grep -rn "payment_currency\|PaymentCurrency" src/`):

| Файл | Что сделать |
|---|---|
| `src/types/index.ts:19` | `PaymentCurrency` → переименовать в `Currency` (значения те же: `'EUR' \| 'PLN' \| 'BYN'`) |
| `src/types/index.ts:32` | в `Student`: `payment_currency: PaymentCurrency` → `balance_currency: Currency \| null` |
| `src/types/index.ts:37` | `balance: number` перенести из `StudentExtended` в `Student` |
| `src/types/index.ts:58` | в `CreateStudentInput`: `payment_currency?` — **удалить**, поля больше нет в API (см. §1.2) |
| `src/types/index.ts:68` | в `UpdateStudentInput`: `payment_currency?` — **удалить**, поля больше нет в API (см. §1.2) |
| `src/components/students/StudentsTable.tsx:16,18,218` | переименовать тип и константу лейблов; учесть `null` — фолбэк `'—'` там уже есть |
| `src/components/students/CreateStudentDialog.tsx:28,30,48,73,89,162` | переименовать поле; см. §1.2 про дефолт |
| `src/components/students/EditStudentDialog.tsx:31,33,66,108,149,175,267` | переименовать поле; см. §1.2 про блокировку селекта |

### 1.2 Селекта валюты в формах ученика больше нет

Поле **удалено** из `CreateStudentDto` и `UpdateStudentDto`: задать валюту руками нельзя ни при каком балансе. При `balance = 0` её запрещает CHECK-констрейнт в БД (`balance = 0 ⟺ balance_currency IS NULL`), при `balance ≠ 0` менять валюту нельзя, пока остаток не израсходован. Единственный источник валюты — движок баланса: её устанавливает первый платёж или ручная корректировка (§2.5).

Что сделать в UI:

- **Create / Edit**: убрать селект валюты из форм и поле из типов. Глобальный `ValidationPipe` поднят без `whitelist`, поэтому лишнее поле не отсекается, а доезжает до Prisma и роняет запрос — не отправляйте его.
- В **чтении** поле остаётся: `balance_currency` приходит в `Student` и в ответах баланса. Значение `null` рендерите как «—» или «не задана».
- Если валюту нужно сменить, а на балансе деньги — это делается корректировкой баланса до нуля (§2.5), после чего валюту установит следующий платёж.

### 1.3 Баланс в списках учеников

`GET /students` теперь возвращает `balance` и `balance_currency` в каждом элементе. Раньше баланс был доступен только через `GET /students/:id`.

Возможность: показать колонку «Баланс» в `StudentsTable.tsx` без дополнительных запросов. Формат — `${balance} ${symbol}`, где символы: `EUR → €`, `PLN → zł`, `BYN → р`. При `balance === 0` показывайте `0` без валюты.

### 1.4 Валюты планов

`CreatePlanInput.plan_currency` (`src/types/index.ts:84`) сейчас объявлен как `'USD' | 'EUR' | 'PLN' | 'BYN' | 'RUB'`. **`USD` и `RUB` удалены из БД и API** — сузьте до `'EUR' | 'PLN' | 'BYN'`. Отправка `USD`/`RUB` теперь вернёт 400 от валидации.

Заодно `Plan.plan_currency` (`src/types/index.ts:75`) типизирован как `string` — стоит сузить до `Currency`.

**Важно про создание плана**: для `PLN`/`EUR` с ценой > 0 бэкенд синхронно создаёт продукт и цену в Stripe. Если Stripe недоступен, вернётся **503 Service Unavailable** и план **не будет создан**. Обработайте 503 отдельным сообщением: «Платёжный сервис недоступен, план не создан. Попробуйте позже». Обычный ретрай безопасен — план не остаётся в полусозданном состоянии.

### 1.5 Старый маршрут отчёта — работает, но устарел

`POST /telegram/send-lessons-cost-to-admin` (`src/api/telegram.ts:24`, используется в `src/components/students/StudentReportDialog.tsx`) **сохранён полностью**: то же тело, те же гварды, тот же `204 No Content`. Ломать ничего не нужно.

Но логика переехала, и у него появился канонический аналог `POST /payments/invoices`, который **возвращает тело со ссылкой на оплату**. Рекомендуется мигрировать: тогда админ увидит ссылку прямо в интерфейсе, а не только в Telegram. См. §2.1.

## 2. Новые эндпоинты

Все — под `JwtAccessGuard + AdminAccessGuard`, то есть **только для роли ADMIN**. Префикс API — `/api` (в `apiClient` он уже настроен, пути ниже указаны без него).

Ошибки приходят в формате `{ statusCode, path, message: string | string[] }` — как и везде в проекте; `api-client.ts` уже показывает их тостом на не-401.

### 2.1 `POST /payments/invoices` — выставить счёт

**Запрос:**
```ts
{ student_id: number; start_date: string; end_date: string }  // даты в формате '2026-08-01'
```

**Ответ 201:**
```ts
{
  payment_id: number
  student_id: number
  amount: number          // целые единицы валюты: 160 = 160 PLN
  currency: 'EUR' | 'PLN' | 'BYN'
  lessons_count: number   // только платные занятия
  link: string | null     // null для BYN и когда Stripe недоступен
}
```

Что делает: тратит остаток баланса на неоплаченные занятия, считает оставшееся, создаёт счёт, для PLN/EUR генерирует Payment Link и **в любом случае отправляет отчёт админу в Telegram**.

**Ответы 400** — покажите `message` пользователю как есть, он информативен:

| Ситуация | Сообщение |
|---|---|
| Нет неоплаченных занятий | `По заданному периоду нет ожидающих оплату уроков` |
| Занятия в разных валютах | `У ученика {имя} занятия в разных валютах (PLN, EUR) — счёт не выставлен` |
| Остаток в другой валюте | `У ученика {имя} на балансе 40€, а занятия периода в PLN — счёт не выставлен. Сначала израсходуйте или скорректируйте остаток.` |
| Некорректный период | `Начало периода позже его конца` / `Некорректный период` |
| Ученик удалён | `Студент удален` |

**404**: `Студент не найден`.

UI-подсказки:
- `link === null` при `currency === 'BYN'` — это норма, не ошибка. Покажите «Оплата в BYN — ссылка не требуется, ожидается чек».
- `link === null` при PLN/EUR — Stripe не ответил. Отчёт админу ушёл, но без ссылки. Покажите предупреждение и кнопку «Выставить счёт заново».
- Ссылку удобно дать копировать в один клик.

### 2.2 `DELETE /payments/invoices/:id` — отменить счёт

Ответ **204**. Деактивирует ссылку в Stripe и переводит счёт в `CANCELED`.

**400**: `Отменить можно только неоплаченный счёт` — кнопку «Отменить» показывайте только для счетов в статусе `PENDING`.
**404**: `Счёт не найден`.

### 2.3 `GET /payments` — история операций

**Query-параметры** (все опциональные):

| Параметр | Тип |
|---|---|
| `student_id` | `number` |
| `status` | `'PENDING' \| 'SUCCEEDED' \| 'CANCELED' \| 'FAILED' \| 'REQUIRES_ATTENTION'` |
| `type` | `'STRIPE_PAYMENT' \| 'STRIPE_REFUND' \| 'MANUAL_ADJUSTMENT' \| 'LEGACY_OPENING_BALANCE'` |
| `from` | `string` (дата) |
| `to` | `string` (дата) |

**Ответ 200** — массив, отсортирован по `created_at` убыванию:
```ts
{
  id: number
  student_id: number
  type: 'STRIPE_PAYMENT' | 'STRIPE_REFUND' | 'MANUAL_ADJUSTMENT' | 'LEGACY_OPENING_BALANCE'
  status: 'PENDING' | 'SUCCEEDED' | 'CANCELED' | 'FAILED' | 'REQUIRES_ATTENTION'
  amount: number            // ЗНАКОВАЯ: списания и возвраты отрицательные
  currency: 'EUR' | 'PLN' | 'BYN'
  period_start: string | null
  period_end: string | null
  lessons_count: number | null
  comment: string | null
  paid_at: string | null
  created_at: string
}
```

> **Пагинации нет** — эндпоинт возвращает всё, что подошло под фильтр. Если история разрастётся, фильтруйте по `student_id`/периоду. Серверная пагинация — потенциальная доработка бэкенда.

Рендер `amount`: отрицательные значения показывайте со знаком и другим цветом — это списание или возврат.

### 2.4 `GET /payments/students/:student_id/balance` — баланс и его расход

**Ответ 200:**
```ts
{
  student_id: number
  balance: number
  balance_currency: 'EUR' | 'PLN' | 'BYN' | null
  allocations: Array<{
    lesson_id: number
    lesson_date: string
    amount: number
    currency: 'EUR' | 'PLN' | 'BYN'
  }>
}
```

`allocations` — занятия, которые сейчас оплачены с баланса, по убыванию даты. Полезно показать в карточке ученика: «Оплачено занятий: N» со списком дат.

**404**: `Студент не найден`.

### 2.5 `POST /payments/students/:student_id/balance/adjust` — ручная корректировка

**Запрос:**
```ts
{
  amount: number              // ≠ 0, знаковая: отрицательная — списание
  currency?: 'EUR' | 'PLN' | 'BYN'  // ОБЯЗАТЕЛЬНА при нулевом балансе
  comment: string             // 3–500 символов, обязателен
}
```

**Ответ 200:**
```ts
{
  balance: number
  balance_currency: 'EUR' | 'PLN' | 'BYN' | null
  affected_lessons: Array<{ lesson_id: number; amount: number; new_status: string }>
}
```

`affected_lessons` — занятия, у которых изменился статус оплаты. Покажите итог: «Оплачено занятий: 3» / «Снята оплата с 1 занятия».

**400:**

| Ситуация | Сообщение |
|---|---|
| Баланс 0, валюта не передана | `Баланс пуст — укажите валюту операции` |
| Валюта не совпадает с остатком | `На балансе 40 EUR — корректировка возможна только в этой валюте` |
| Списание больше доступного | `Недостаточно средств: не хватает 70` |

UI-подсказки для формы корректировки:
- Селект валюты показывайте **только когда `balance === 0`**; иначе валюта предопределена — покажите её как статичный текст.
- Комментарий обязателен, минимум 3 символа — валидируйте на клиенте.
- «Недостаточно средств» — это про сумму *баланс + оплаченные занятия, с которых можно снять оплату*, а не только про баланс. Не пытайтесь считать лимит на клиенте, доверьтесь ответу сервера.

### 2.6 `POST /payments/:id/apply` — применить отложенный платёж

Нужен для редкой ситуации: платёж пришёл в валюте, конфликтующей с ненулевым остатком другой валюты (гонка или оплата старой ссылки). Деньги получены, но к балансу не применены — платёж лежит в статусе **`REQUIRES_ATTENTION`**.

Ответ — тот же `AdjustBalanceResultDto`, что в §2.5.

**400:**
- `Применять можно только платежи в статусе REQUIRES_ATTENTION`
- `Конфликт не разрешён: на балансе 40 EUR, платёж в PLN` — админ ещё не обнулил остаток.

UI: в истории (§2.3) платежи со статусом `REQUIRES_ATTENTION` подсветите красным, дайте кнопку «Применить» и подсказку: «Сначала обнулите остаток в другой валюте, затем примените платёж».

### 2.7 Вебхук — фронтенда не касается

`POST /payments/stripe/webhook` публичный, без авторизации, вызывается только Stripe. Не трогайте его и не выводите в UI.

## 3. Бизнес-правила, которые обязан отражать интерфейс

Эти правила бэкенд применяет жёстко и возвращает 400. Хороший UI предупреждает о них **до** отправки запроса.

### 3.1 Одна валюта на ученика в один момент

Нельзя назначить занятие по плану в валюте, конфликтующей с деньгами ученика. Конфликт — это:

- **ненулевой остаток на балансе в другой валюте** (действует в любом месяце);
- **платные занятия того же календарного месяца в другой валюте**, включая уже оплаченные.

Ошибки при создании занятия (`POST /lessons/single`, регулярные, перенос) и при смене плана:

```
На балансе ученика 40 EUR — нельзя назначить занятие по плану в PLN.
Сначала израсходуйте или скорректируйте остаток.
```
```
В этом месяце у ученика уже есть занятия в EUR — нельзя добавить занятие в PLN.
Смените планы существующих занятий или назначьте это занятие на следующий месяц.
```

Что сделать в UI: в диалогах создания занятия **фильтруйте список планов по валюте**, если она у ученика уже определена (`balance_currency !== null` либо в выбранном месяце уже есть занятия). Показывайте недоступные планы задизейбленными с подсказкой, а не прячьте — иначе админ не поймёт, куда делся план.

Прошлые месяцы под правило не попадают — исторические расхождения работу не блокируют.

Бесплатные (`is_free`), пробные (`is_trial`) и нулевые по цене занятия из проверки исключены — их можно назначать в любой валюте.

### 3.2 Смена валюты возможна со следующего месяца

Практическое следствие §3.1: пока в текущем месяце есть занятия в PLN, добавить в него EUR-занятие нельзя. Со следующего месяца — можно, если баланс нулевой. Это стоит объяснить в подсказке рядом с селектом валюты.

### 3.3 Переплата и автопогашение

Оплатили 200 PLN при счёте на 160 → 4 занятия становятся оплаченными, 40 PLN остаётся на балансе. Когда админ назначит **пятое** занятие, оно **автоматически** станет оплаченным, баланс уйдёт в 0, а `balance_currency` — в `null`.

UI не должен этому мешать: после создания/отмены/удаления занятия **инвалидируйте кэш** react-query по ключам ученика, баланса и списка занятий — статусы оплаты могли измениться на сервере без явного запроса от фронтенда.

Список операций, после которых нужна инвалидация: создание занятия (одиночного, регулярных, переноса), отмена, удаление, переключение `is_free`, смена плана за период, корректировка баланса, выставление счёта.

### 3.4 Отмена и пропуск — разные вещи для денег

- **`CANCELLED`** у оплаченного занятия → деньги возвращаются на баланс и тут же уходят на другие неоплаченные занятия.
- **`MISSED`** → оплата **сгорает**, деньги не возвращаются.
- **`RESCHEDULED`** → оплата ждёт и переезжает на новое занятие при создании переноса.

Это стоит написать в подтверждении отмены: админ должен понимать финансовое последствие выбора. Формулировка вроде «Пропуск: оплата за занятие сгорает» / «Отмена: деньги вернутся на баланс».

### 3.5 Ссылка на оплату не выдаётся ученику без занятий

Валюту счёта брать неоткуда. Кнопка «Выставить счёт» для ученика без неоплаченных занятий в периоде вернёт 400 — либо задизейбльте её, либо покажите понятное сообщение из ответа.

## 4. Что можно построить (предложения, не обязательные)

Бэкенд это уже поддерживает, фронтенд-части нет:

1. **Секция «Оплаты» в карточке ученика**: баланс + валюта, список активных аллокаций (§2.4), история операций с фильтром `student_id` (§2.3), кнопка ручной корректировки (§2.5).
2. **Колонка «Баланс» в таблице учеников** — данные уже приходят (§1.3).
3. **Страница «Платежи»**: общая история с фильтрами по статусу/типу/периоду, отдельный акцент на `REQUIRES_ATTENTION` и `FAILED`.
4. **Замена кнопки отчёта на `POST /payments/invoices`** в `StudentReportDialog.tsx` — чтобы показывать ссылку на оплату в интерфейсе, а не только слать в Telegram (§2.1).
5. **Индикатор оплаты в расписании** — статусы занятий `PENDING_PAID` / `COMPLETED_PAID` меняются автоматически, их полезно визуально отличать от `*_UNPAID`.

## 5. Справочник значений

```ts
type Currency = 'EUR' | 'PLN' | 'BYN'

const CURRENCY_SYMBOLS: Record<Currency, string> = {
  EUR: '€',
  PLN: 'zł',
  BYN: 'р',
}

type PaymentType =
  | 'STRIPE_PAYMENT'          // счёт/оплата через Stripe
  | 'STRIPE_REFUND'           // возврат, сумма отрицательная
  | 'MANUAL_ADJUSTMENT'       // ручная корректировка админом
  | 'LEGACY_OPENING_BALANCE'  // технический перенос исторического баланса

type PaymentStatus =
  | 'PENDING'             // счёт выставлен, оплаты нет
  | 'SUCCEEDED'           // деньги получены и применены
  | 'CANCELED'            // счёт отменён
  | 'FAILED'              // оплата не прошла
  | 'REQUIRES_ATTENTION'  // деньги получены, но не применены — конфликт валют
```

**Все суммы — целые единицы валюты**, не копейки. `40` означает 40 PLN. Никаких делений на 100 на фронтенде не нужно.

## 6. Чего делать не нужно

- **Не интегрируйте Stripe.js / Elements.** Оплата идёт по Payment Link — это внешняя страница Stripe, фронтенд только показывает URL.
- **Не считайте баланс на клиенте.** Единственный источник истины — сервер; распределение денег по занятиям делается под блокировкой в транзакции.
- **Не пытайтесь угадать, хватит ли средств** перед списанием: правило учитывает и баланс, и оплаченные занятия. Отправляйте запрос и показывайте ответ.
- **Не показывайте `stripe_*` идентификаторы** — они не выводятся в API и админу не нужны.

## 7. Как проверить свою работу

Бэкенд-часть покрыта: 528 unit-тестов и 180 e2e (`cd backend && yarn test:unit`, `yarn test:e2e --runInBand`).

Для ручной проверки фронтенда полезен сценарий из `plan.md` §14:

1. Завести ученика (валюту не задавать).
2. Назначить 4 занятия текущего месяца по PLN-плану (40) → счёт на 160 со ссылкой.
3. Оплатить 200 → 4 занятия оплачены, 40 на балансе, валюта `PLN`.
4. Попробовать назначить занятие по BYN-плану → 400 (конфликт валют).
5. Назначить пятое PLN-занятие → само становится оплаченным, баланс 0, валюта `null`.
6. Назначить BYN-занятие на следующий месяц → проходит.
7. Отменить одно PLN-занятие → 40 возвращается на баланс.

Живые ключи Stripe для шагов 2–3 нужны в `backend/.env.development`; без них шаги 1 и 4–7 всё равно проверяются.
